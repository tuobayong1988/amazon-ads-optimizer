# V340版本综合修复报告：同步健康监控、Token竞态修复与大账户保护

**版本**: `v340`  
**状态**: 已成功部署到生产环境

## 1. 核心问题背景

在对V339版本的部署后分析中，我们发现账户`90027`存在两个P0级（最高优先级）的严重问题：

1.  **数据同步静默失败**：该账户的数据同步任务（`syncAll`）虽然在数据库中记录为“完成”，但实际同步的记录数为0，导致其数据范围始终停留在49天前，V339的分批修复未能生效。
2.  **API写操作认证失败**：该账户的所有优化指令（如竞价调整）均因`401 Unauthorized`错误而失败，表明其API Token已失效，且自动刷新机制未能成功恢复。

为解决这些深层问题，我们实施了V340版本，旨在从根本上提升数据同步的**可观测性、健壮性和可操作性**。

## 2. V340版本修复与增强功能详解

V340版本包含五项关键更新，全面解决了上述问题并建立了更完善的系统健康监控体系。

### 2.1. 【P0-1】`syncAll` 详细分步日志系统

为彻底解决“静默失败”问题，我们为核心的`syncAll`方法引入了统一的`runStep`诊断日志系统。

- **精细化追踪**：现在，`syncAll`中的**全部27个同步步骤**（如同步SP广告活动、同步SB搜索词等）的开始、结束、耗时、同步记录数以及任何捕获到的异常都会被详细记录。
- **智能汇总报告**：每个账户的`syncAll`任务完成后，系统会生成一份包含所有步骤详情的汇总报告，清晰展示成功、失败的步骤和各自的性能指标。

| 功能 | 描述 |
| :--- | :--- |
| **可观测性** | 精确到每个子步骤的性能和结果，快速定位瓶颈或失败点。 |
| **问题定位** | 不再有“静默失败”，任何步骤的异常都会被明确记录和报告。 |

### 2.2. 【P0-2】手动触发全量同步API

为了赋予运维人员更强的干预和修复能力，我们新增了一个API端点，用于手动触发任意账户的全量同步。

- **API端点**: `POST /api/ops/force-sync`
- **功能**: 支持指定`accountId`和同步层级（`full`, `fast`, `minimal`），立即为该账户启动一次完整的同步任务。
- **应用场景**: 可用于紧急数据修复、问题排查（如强制为90027执行90天同步）或新功能验证。

### 2.3. 【P0-3】API Token刷新竞态条件修复

我们定位并修复了导致账户`90027`所有API写操作失败的根因：**Refresh Token并发刷新冲突**。

- **问题根因**：6个不同的API凭证（Profile）共享同一个Refresh Token，当它们的Access Token同时过期时，会并发使用同一个Refresh Token去请求新的Access Token，导致Amazon OAuth服务器拒绝部分请求。
- **修复方案**：我们实现了一个**全局级别的Refresh Token刷新锁**。现在，当多个API实例需要刷新时，只有第一个实例会真正执行刷新操作，其他实例将等待并安全地复用刷新结果，彻底杜绝了竞态条件。

### 2.4. 【P1-1】同步健康监控告警

基于新的详细日志系统，我们建立了自动化的同步健康监控告警机制。

- **触发条件**: 当任何一个账户的`syncAll`任务完成，但总同步记录数`totalSynced`为0时。
- **告警动作**: 系统会自动触发一个**`critical`级别的告警**，并将包含完整诊断信息（失败步骤、错误详情等）的告警事件写入`anomaly_alert_logs`数据库表，以便后续追踪和分析。

### 2.5. 【P1-2】大账户自适应保护机制

为防止超大账户（如拥有3360个广告活动的`90027`）的同步任务因耗时过长或API调用过于频繁而影响系统稳定性，我们引入了自适应保护机制。

- **触发条件**: 当账户的广告活动总数超过1000个时自动激活。
- **保护措施**：
    1.  **步骤间延迟**：在`syncAll`的每个步骤之间自动增加3秒的延迟，平滑API调用峰值。
    2.  **超时保护**：为单个账户的同步任务设置45分钟的超时上限，防止其无限期执行，阻塞整个同步调度队列。
