# v791+ 仪表盘首屏深度优化设计

## 目标

本次升级围绕截图中的五项后续建议展开：租户/账号级首屏快照短 TTL 缓存、数据新鲜度与归因窗口提示、关键数据缺失时后台自愈补数、按需诊断扫描体验优化，以及多账号切换时的快照预取。核心原则是在不牺牲真实数据准确性、多租户隔离和同步覆盖语义的前提下，进一步降低登录首屏和账号切换时的慢查询阻塞风险。

## 服务端方案

| 模块 | 改造方案 | 正确性约束 |
| --- | --- | --- |
| `analytics.getDashboardBootstrap` | 使用规范化后的 `tenant:user:account:start:end:days` 快照缓存键，TTL 控制在 30 秒级；返回 `cacheMeta`、`dataFreshness` 和 `dataCoverage` | 缓存键必须包含用户与账号维度，不能跨租户复用；账号访问校验必须先于数据查询 |
| 同步完成后失效 | 在 `updateSyncJob` 进入 `completed/failed/cancelled` 终态时，精准失效该账号相关仪表盘快照缓存 | 只失效受影响账号的快照，避免清空全局缓存导致缓存击穿 |
| 数据新鲜度 | 基于最后成功同步时间、当前查询区间数据行数、归因成熟度和是否缺日构造状态：`fresh/stale/empty/attribution_pending` | 新鲜度只是展示层提示，不改变 KPI 的真实聚合口径 |
| 自愈补数 | 当最近区间有账号但无日聚合数据、或者最近成功同步过旧且没有活跃同步任务时，创建低优先级 `sync_task_queue` 补数任务 | 必须去重，避免每次打开首屏重复排队；任务 metadata 记录触发来源和查询区间 |
| 诊断扫描短缓存 | 在 dashboard recommendation / intelligent recommendation 扫描层增加 2 分钟账号级缓存；执行动作成功后失效 | 缓存不能阻止执行后结果消失，所有 execute mutation 必须主动失效 |

## 客户端方案

| 模块 | 改造方案 | 用户体验 |
| --- | --- | --- |
| Home 首屏 | 读取 `dataFreshness` 和 `cacheMeta`，在 KPI 区域展示轻量提示：数据最新、归因窗口内、同步较旧或已触发补数 | 用户能区分“暂无数据”“数据仍在归因窗口”“正在后台补数” |
| 手动刷新 | 刷新时同时重新拉取快照并保持按需增强数据逻辑不变 | 避免刷新重新触发旧慢链路 |
| 按需诊断 | 诊断按钮展示短缓存与扫描状态提示，用户点击才加载三类建议卡片 | 保留准确性，减少登录首屏自动扫描 |
| 多账号切换 | 在 `useGlobalAccountId` 解析账号后，对当前账号和同店铺相邻站点账号预取 `analytics.getDashboardBootstrap` | 账号切换后优先命中客户端和服务端短缓存，减少可感知等待 |

## 版本边界

本设计不引入新的长期后台进程，不改变 AWS EB 应用部署形态，不新增数据库迁移，优先复用现有 `apiCache`、`sync_task_queue` 和 tRPC 查询能力完成闭环。
